# 邮件草稿、审核、单封发送和回复同步

## 四个分开的业务状态

1. **客户同意开发**：在“客户与 RFQ 审核”里由用户决定；不是邮件内容审核。
2. **邮件内容审核**：用户打开具体邮件并点击“审核此封”。系统按当前版本核对主题、正文、收件地址、来源钩子和状态。邮件改版后原审核失效。
3. **收件邮箱确认**：点击“确认此收件邮箱”表示用户确认所填地址正确。系统保存状态为“用户已确认”、时间和确认来源；不要求官网证明，也不标记成系统独立核验。更改地址后需重新确认，且邮件版本要重新审核。
4. **单封发送**：仅用户对已审核的这封邮件在应用中点击发送并确认后执行。没有无人值守发送、批量发送或自动发送整个五封序列。

若“审核此封”报客户未同意：这是客户审核状态门槛。引导用户使用开发信卡片上的“前往客户审核（同意开发）”，定位到对应客户并由用户决定；不得自动替用户批准。若客户已剔除，先由用户把其状态改回待审核，再重新决定是否同意开发。

公司身份待核验是独立资料状态；除非当前版本另有明确业务规则，不应把它伪装为收件邮箱所有权验证，也不应要求用户证明自己公司或邮箱归属。

## 写作规范

- 依真实 RFQ、用户提供的业务事实或明确记录的资料写作。不编造公司事实、个人关系、库存、工艺能力、交期、价格或已经安排的拜访。
- 本项目默认五封序列：第1封当天；第2、3封分别在上一封后2天且无回复时；第4、5封分别在上一封后5天且无回复时。间隔是建议，不应把未批准邮件自动排成发送任务。
- 每封英文主题最多6个单词、正文最多50个英文单词（按项目验证器口径）。问候、短段落、实际签名和买家导向的轻量问题要清楚。
- 已有五封草稿默认保留；重复点击生成应报告跳过。用户选择重新生成时保留历史版本，不能覆盖已审核正文。

## 发送前/发送后

- 发送前看实际收件人、主题、正文、附件和审核版本；每次确认只授权这一封。
- 后端须核对当前内容哈希/版本、审批状态、邮箱格式、用户确认记录、禁止列表、暂停状态、前序邮件和收件同步状态。不要仅依赖前端按钮是否灰显。
- 发送记录包括 Message-ID、时间、收件人、SMTP 返回和错误。SMTP 已接受代表服务器接受提交，不等于收件人收到或阅读。
- 再核对 Outlook 已发送文件夹。状态分别为 SMTP 已接受、已发送文件夹找到、结果待核实；结果不明时不重试、不重复发送。
- 已发送副本保存失败与 SMTP 发送失败是两回事，不能据此再次发送。
- 回复同步仅在读到真实入站邮件并正确关联后报告“已回复”；有回复、退信或停止联系信号时，暂停后续邮件。没有真实回复记录时标为未验证。

## 常用只读检查

- `GET /api/outreach`：当前邮件、版本、状态、审批和发送核查字段。
- `GET /api/outreach/messages/:id/review`：某一草稿当前是否可审核及其具体原因。
- `GET /api/mail/settings`：只读邮件连接状态；禁止输出密钥或授权令牌。
- `GET /api/health`：本机应用健康状态。

正常业务修改应经 UI 或现有带 CSRF 保护的业务路由。禁止直接 SQL 把客户改成已同意、把草稿改成已批准/已发送，或在调试时绕开发送确认。

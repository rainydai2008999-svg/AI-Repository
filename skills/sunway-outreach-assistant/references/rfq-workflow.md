# RFQ 采集、导入和客户审核

## 操作入口

- 总览的 A：重新导入已有本地采集文件；不启动浏览器、不访问平台。
- 总览的 B：请求平台采集并同步。每个平台单独读取其运行状态，某一平台失败不能覆盖其他平台结果。
- 客户与 RFQ 审核：检查已入库机会、核对 RFQ、筛选、记录人工同意/剔除/待补资料。
- 开发信审核页中的客户卡片是邮件工作区，不等同于客户与 RFQ 审核。

## 导入和采集规则

1. 阅读 `sync.js`、`monitor-inbox.js`、`rfq-workflow.js`、`platform-collector.js` 及对应 API 路由，确认当前接受的文件契约和平台能力。
2. 候选列表、运行报告和正式 RFQ 文件是不同数据类型。只有符合导入契约的记录才导入；详情未读到的候选继续留在待处理队列，不冒充已核验询盘。
3. 以平台与稳定 RFQ ID 去重；无 ID 时使用规范化原始链接。不能只按标题或买家姓名合并。不同 RFQ ID 必须保留，即使内容相似；跨平台相似项标为疑似重复。
4. 日期保留平台原文和时区。未知时区、日期边界、未读取正文、详情错误要分别说明，不补造精确时间、公司、国家、数量或联系方式。
5. 平台字段更新时保留人工审核状态、审核理由、备注、联系人确认和邮件组。需求正文、规格、数量、期限发生重要变化时记历史并提示重新审核。
6. 新 RFQ 默认“待审核”。即使某客户曾获同意，新 RFQ 仍须逐条审核。公司身份待核验或邮箱缺失不应使真实高匹配 RFQ 从 RFQ 审核列表消失。
7. 若旧范围或关键词清单存在于项目配置中，应检查覆盖状态而不是凭记忆宣称完成。按关键词记录时间窗口、分页范围、候选数、详情数及失败项。
8. 失败平台不得推进上次成功检查时间，也不能把读取失败表示为“无匹配结果”。历史文件导入不能冒充实时平台读取。

## 匹配与审核

- 综合标题、需求正文、采购对象和具体产品类别判断；单一通用词（例如 shaft）不够判为高匹配。
- 保留清晰的匹配理由和技术缺项。采购意图或原始正文不足时，标为待核验，不降级成“已核实的不匹配”。
- 对时间只显示日期或“几天前”的记录，将时间确定性与产品匹配度分开。
- 用户审核时核对 RFQ 原文、规格/数量、国家、买家展示名及来源。平台展示的买家名字不自动等于可核实决策人。

## 页面和状态验收

- 保存后重新读取数据库/API，并在审核页面确认记录与来源相符。
- 按首次发现时间 `discovered_at` 从新到旧显示 RFQ；时间缺失时才回退到最近一次观察时间。不要用混合格式、时区不统一的 `posted_at` 做跨平台总排序。相同发现时间用 RFQ ID 保持顺序稳定。
- 每轮导入后按 RFQ ID 对账数据库和审核页：分别报告新增、更新、重复、失败；更新的旧 RFQ 不算新询盘，也不要覆盖人工审核决定。刷新页面后确认新发现记录位于前部。
- 报告本轮新增、更新、重复、跳过、失败及理由。页面统计不是本轮运行证据。
- 用户明确要求把 RFQ 报告发给指定收件人时，先按平台、RFQ ID 和采集批次核对数据库/API，分清新增与更新，标出平台失败、未读详情及明显误匹配/疑似重复；使用用户指定的邮件服务商，不用小助手的 Outlook 配置代替 Gmail。发件记录只证明已发送到邮件服务，不证明对方已收到或阅读。
- 新增 RFQ 不自动同意客户、不批准草稿、不创建发送授权、不发送邮件。
- Global Sources 等站点若返回 503、登录页、验证码或权限提示，记录看见的事实和队列位置；不绕过站点保护。
